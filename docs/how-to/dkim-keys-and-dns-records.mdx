# DKIM keys and DNS records

:::note
API version `v1alpha1`. The `MailDomain` controller creates and rotates
the DKIM keys and keeps the list of required DNS records; the `MailServer`
that serves the domain hands the active keys to Rspamd, which signs with
them ([below](#what-the-data-plane-does-with-the-keys)). Design:
[ADR 0011](../decisions/0011-dkim-keys-and-rotation.md),
[ADR 0012](../decisions/0012-dns-records-and-dmarc.md) and
[ADR 0013](../decisions/0013-never-unsigned-guard.md).
:::

## Prerequisite: a grant

A `MailDomain` is only active when a `MailDomainGrant` names its
namespace ([domain authorization](../concepts/domain-authorization.md)),
or the operator runs with `--domain-authorization=unrestricted`. Without
it `kubectl get maildomains` shows `Authorized` as `False`, and the
domain gets no key, no records and no signing.

## Choose how keys are made

A domain always signs. There are two ways to get the keys.

### Your own keys (recommended for production)

The keys stay in your GitOps repository (SOPS, sealed secrets) or an
external secret store, so a restore needs no key recovery, and k8up does
not have to back up Secrets. Create an RSA key of at least 2048 bits or
an Ed25519 key:

```console
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out s2026a.key
openssl genpkey -algorithm ED25519 -out s2027a.key
```

and reference each key from `spec.dkim.keys`:

<CodeBlock language="yaml" title="config/samples/cnms_v1alpha1_maildomain-byo-keys.yaml">{ByoKeys}</CodeBlock>

- The Secret must be in the namespace of the `MailDomain`. A key that is
  missing, too short (RSA below 2048 bits), ECDSA or not a private key
  is reported per selector in `DKIMKeysValid`; the other keys keep
  working. The Secrets are not watched, so the operator reads them again
  every five minutes (every minute while one is unusable).
- `signing: false` publishes a key without signing with it, before it
  takes over or while you retire it; the status lists it as `pending`
  either way.
- **Rotate by hand:** publish the new key with `signing: false`, wait
  until `kubectl get maildomain -o yaml` shows its record `verified`, flip
  the flags in one commit and remove the old entry after the overlap. The
  overlap has to cover the Postfix queue lifetime (5 days): mail is
  verified on delivery, possibly days after it was signed.
- Replacing the key under a published selector is not a rotation: the
  record no longer matches and `status.records` shows it unverified.

### Keys generated by the operator (quick start)

Without `spec.dkim.keys` the operator generates an RSA-2048 key, and an
Ed25519 key with `ed25519: true`. `rotation` replaces the key on an
interval:

<CodeBlock language="yaml" title="config/samples/cnms_v1alpha1_maildomain-ed25519.yaml">{Ed25519}</CodeBlock>

- Each key is an immutable Secret `<maildomain>-dkim-<selector>` with
  the PEM in `private.key`. The selector is `<prefix>-<yyyymmdd>` (UTC
  date of creation; Ed25519 `<prefix>-ed25519-<yyyymmdd>`).
- A new domain signs with its first key at once; the record is shown as
  not verified until you publish it.
- **Rotation:** when the active key is older than `interval`, a new key
  is created and its record is published as `pending`; it signs once its
  record has been verified for 15 minutes. The old key stays published
  as `retiring` for the `overlap` (default 120h), then its record leaves
  the required set and its Secret is deleted. A record that never
  verifies keeps the old key signing, and `DKIMRotation` stays `False`
  with reason `AwaitingDNS`.
- The progress is stored in the annotation `cnms.rpp.gmbh/rotation` on
  the `MailDomain`, because it has to survive a restore without status.
  **Tell your GitOps tool to ignore this annotation**, as for any other
  field the operator writes.
- The key Secrets have no owner reference and are **kept** when the
  `MailDomain` is deleted or revoked, so a re-created domain does not
  rotate. Delete them yourself with
  `kubectl delete secrets -l cnms.rpp.gmbh/maildomain=<name>`.
- **Restore:** Secrets are not part of a k8up backup. With the Secrets
  and without the annotation the operator derives the state again (the
  oldest key per algorithm is active) and never regenerates a key that
  exists. After a restore without the Secrets the domain gets new keys.
- **Key loss:** a new key means a new selector and a new DNS record. When
  the loss and the new key fall on the same UTC day, change
  `spec.dkim.selectorPrefix` so that the selector differs.

## What the data plane does with the keys

The `MailDomain` names its server in `spec.serverRef`. For every domain
that references it and is authorized, the `MailServer` takes the **active** keys (not the pending or
retiring ones), reads their Secrets and gives them to its Rspamd pods
as read-only files; the configuration names the key files and
selectors, never key bytes. With both algorithms enabled every message
carries an RSA and an Ed25519 signature.

- **Who is signed:** mail of authenticated senders (submission) and the
  non-SMTP mail of Postfix itself. Unauthenticated mail (from the
  Internet or from other pods) and bounces generated by Postfix are not
  signed.
- **Never unsigned:** if a signed mail of a served domain has not got a
  signature for every active key, the mail is not sent: the client gets
  `451 4.7.1 DKIM signing unavailable, try again later` at the end of
  DATA and keeps the mail. This covers a domain without a key yet, a
  key Secret that is missing or unusable, and a bug in the check
  itself. Inbound mail of the domain is not affected, and the rest of
  the `MailServer` keeps rolling out. `DKIMKeysAvailable` on the
  `MailServer` is `False` and names each domain and key that is
  missing; it never feeds `Ready`. The operator looks again every
  minute. Fix the key (create the Secret, correct its content) and the
  deferred mail goes out on the client's next retry.
- **Rotation:** a switch of the active key changes the signing
  configuration, so it goes through the validation Job and a rolling
  update of Rspamd, like any other configuration change. Pending and
  retiring keys are not mounted: only the keys that sign are.
- **Not covered:** the guard itself does not bind the login to the sender;
  that is the envelope sender binding of Postfix and, for the accounts that
  the operator manages, the header From check of the guard (see
  [DKIM signing](../concepts/dkim-signing.md)). Authenticated mail whose `From`
  is missing, has no domain or is not in a served domain is rejected with
  `554 5.7.1`. A message
  with several `From` addresses, one of them in a served domain, is
  rejected with `554 5.7.1`, because it can never be signed; locally
  submitted mail of that kind bounces to its sender
  ([ADR 0013](../decisions/0013-never-unsigned-guard.md)).

## DNS records

`status.records` lists every record the domain needs (DKIM of each
published key, SPF, DMARC, MTA-STS, TLS-RPT, and the MX record that points
at the hostname of its server) with its value and whether a lookup found
it. The records of the hostname itself are in the status of the
`MailServer` ([below](#dns-records-you-must-create)):

```console
kubectl get maildomain example-org -o jsonpath='{range .status.records[*]}{.name}{"\t"}{.verified}{"\n"}{end}'
```

<CodeBlock language="yaml" title="config/samples/cnms_v1alpha1_maildomain.yaml">{MailDomainSample}</CodeBlock>

- **SPF** lists the sending sources of the domain (`spec.spf`) and the ones
  of its server (`MailServer.spec.spf`): the record of a domain is the
  union of the two, the sources every domain of a server shares belong on
  the server. With no source at all no record is published and `SPFReady`
  says `NoSendingSources`. Addresses of IP pool claims and relays are
  added in later phases.
- **MX** points at the hostname of the server, `10 <hostname>`, while the
  server serves the domain and its hostname is authorized. It is verified
  when one MX record at the domain points at the hostname (a backup
  exchanger is not compared). CNMS reports and verifies it; you create it.
- **DMARC** follows RFC 9989: `t=y` for `testing`, no `pct`. The Rspamd
  of the data plane ignores `t`, `np` and `psd` on inbound mail. A report
  address in another organizational domain needs a record at its
  receiver; `ReportAuthorization` names it.
- **MTA-STS** is report-only: the status holds the policy text and its
  id, you serve it at `https://mta-sts.<domain>/.well-known/mta-sts.txt`.
  The `mx` host is the hostname of the `MailServer` in `spec.serverRef`
  when it serves the domain (the name in its certificate and HELO), so the
  MX record of your domain has to point at that name. While the server
  does not exist or does not serve the domain there is no policy and
  `MTASTSReady` is `False` with reason `NoMailServer`; while its
  hostname is not authorized the reason is `HostnameNotAuthorized`, and
  the in-cluster name of the Service is never published. A server that
  starts or stops serving the domain, or a renamed hostname, updates the
  policy and its id.
- **The server need not exist yet.** A `MailDomain` whose `serverRef`
  names a missing `MailServer` still authorizes, generates its keys and
  lists its records, so you can prepare DNS first. `ServerFound` is
  `False` (reason `ServerNotFound`) and never feeds into `Ready`.
- **Verification** asks a resolver for the records: the system resolver of
  the pod, or `--dns-resolver=host:port`. Unverified records are checked
  after one minute, backing off to ten; verified ones every hour. A
  resolver error never turns a record to `False`: after three failed
  rounds `RecordsVerified` becomes `Unknown` (`LookupFailing`).
  `Ready` stays `False` until every record is verified.

### `manual` mode (default)

Create the records from `status.records` in your zone yourself.

### `externalDNS` mode

With `spec.dnsMode: externalDNS` and the external-dns `DNSEndpoint` CRD
installed, the operator creates a `DNSEndpoint` `<maildomain>-dns` in the
namespace of the `MailDomain`, one TXT endpoint per TXT record. The MX
record of the domain is not part of it: it is reported and verified, and
you create it (publishing MX, A and AAAA through external-dns is in the
[backlog](../backlog.md)). Without the
CRD `DNSPublished` is `False` with reason `ExternalDNSNotInstalled`, the
records stay in the status, and the CRD is looked up again every five
minutes. An object of that name that the `MailDomain` does not control
is never overwritten (`OwnershipConflict`).

external-dns needs:

- `--source=crd --crd-source-apiversion=externaldns.k8s.io/v1alpha1 --crd-source-kind=DNSEndpoint`,
- **`--managed-record-types=TXT`** (the default covers `A`, `AAAA` and
  `CNAME` only),
- a `--domain-filter` that covers the domain, its own `--txt-owner-id`,
  and no namespace or label filter that hides the `DNSEndpoint`,
- no RBAC for tenants on `dnsendpoints`: whoever can create one in a
  watched namespace bypasses the domain grants.

The DKIM value of an RSA-2048 key is longer than 255 octets. The operator
writes it as one target; whether your provider splits it into
character-strings is not verified, so check that `verified` turns `true`.
If the apex already has a different SPF record, the verification reports
the value it found; external-dns does not take over records it does not
own.

## DNS records you must create

Besides the records of the domains, the hostname of the server needs
records. CNMS lists them in the status and verifies them; it does not
publish them, in `manual` and in `externalDNS` mode alike
([ADR 0014](../decisions/0014-domain-server-binding-and-hostname.md)).

| Record | Name | Value | Where it is listed |
|---|---|---|---|
| `MX` | each domain | `10 <hostname>` | `status.records` of the `MailDomain` |
| `A` / `AAAA` | the hostname | every address of the inbound Service | `status.records` of the `MailServer` |
| `TXT` (SPF) | the hostname | `v=spf1 <server sources> -all` | `status.records` of the `MailServer` |
| `PTR` | each sending address | the hostname | later, with the IP pools (manual rDNS, Phase 7) |

```console
kubectl get mailserver mail -o jsonpath='{range .status.records[*]}{.type}{"\t"}{.name}{"\t"}{.value}{"\t"}{.verified}{"\n"}{end}'
```

- **The addresses come from the inbound Service.** A `LoadBalancer`
  Service gets an `A` or `AAAA` record for every ingress address. The
  condition `AddressRecords` says why none is listed: `ClusterIP`
  Services have no address outside the cluster (`NoExternalAddress`), a
  load balancer that reports a DNS name instead of an address
  (`LoadBalancerHostname`) needs a `CNAME` or alias record from you, and
  `AddressPending` means the Service has no address yet.
- **The SPF record of the hostname** is the HELO identity: receivers check
  it for bounces and for servers that identify themselves by name. It ends
  in `-all`, because only the sources in `MailServer.spec.spf` send as the
  hostname. It is left out when a `MailDomain` of the same name is served
  by this server, because a name holds one SPF record; that domain lists
  the sources of its server. A `MailDomain` of that name on another server
  does not take it over.
- **Nothing here feeds into `Ready`.** `RecordsVerified` and
  `AddressRecords` on the `MailServer` are warnings, and `Ready` of a
  `MailDomain` waits for its own records, the MX record included.
- **Without an authorized hostname nothing is required** and the status
  lists no record: fix `HostnameAuthorized` first.

### The certificate and the hostname

The certificate of the server carries the hostname as its only name. The
domains are not on it, so submission and IMAP clients connect to the
hostname (not to `mail.<domain>`, unless that is the hostname) or verify
it. Applications in the cluster connect to the Service and verify the
hostname; the credential Secret of a `MailServiceAccount` will carry it as
`tlsServerName` (ADR 0008, Phase 3).

A public CA cannot validate the hostname with the HTTP-01 challenge: the
mail load balancer serves no HTTP. Use an issuer with the **DNS-01
challenge**, or a private CA. The in-cluster name of the Postfix Service
(`<server>-postfix.<namespace>.svc.cluster.local`) is only the fallback
name while the hostname is not authorized; a public ACME issuer rejects
it, so a server on the fallback has no certificate from such an issuer
until the hostname is authorized. A name below `cluster.local` is never
accepted as hostname (`HostnameNotAuthorized`).

### Rename the hostname

A rename is a revocation of the old name: the Certificate is re-applied
for the new name at once. The domains keep being served: the running pods
still present the old name, which the Certificate no longer requests,
until the new configuration is validated and rolled out, so TLS clients
that verify the name may fail in that window. A hostname change never
applies the fail-closed configuration (every recipient rejected with a
permanent `554 5.7.1 Relay access denied`), not even while the server is
blocked for another reason, such as a missing directory; then the pods keep
the old name until the blocking input is fixed. Create the `A`/`AAAA`
records and the grant of the new name first, then repoint the MX records of
the domains.

The same window applies when the grant of the hostname is revoked and
the server falls back to the Service name: HELO is self-asserted, and the
mounted certificate Secret is replaced only when the issuer can issue the
new name. A public ACME issuer cannot issue the Service name, so the
Secret with the old name stays mounted until it expires. Fix the grant,
or restore the hostname, to end the window sooner.

`HostnameNotAuthorized` also rejects `cluster.local` and everything below
it. A name such as `foo.default.svc` is not rejected by that rule (it does
not end in `.cluster.local`); in allowlist mode only a name a
`MailDomainGrant` covers for the namespace passes.

## Revoked domains

When the grant goes away the domain stops signing and its status lists no
records. The `DNSEndpoint` is removed 15 minutes later (counted from the
`Authorized` condition; a grant that returns in time keeps it) and the key
Secrets stay.

## Move a domain to another server

Changing `spec.serverRef` moves the domain; it is the one way to hand it
to another `MailServer` of the namespace
([ADR 0014](../decisions/0014-domain-server-binding-and-hostname.md)).
The old server is re-rendered without the domain, like a revoked one: it
stops signing and accepting submission for it with its next validated
rollout. The new server picks the
domain up and signs with the same key Secrets, so the selectors do not
change, and the `DNSEndpoint` stays.

What does not move, and what to check:

- **Mailboxes and queued mail stay on the old server.** Nothing copies
  them. Let the queue drain first, and move the mailbox data yourself if
  the old server has mailboxes.
- **MX and MTA-STS.** Point the MX record at the new server before the
  old one stops answering. Receivers cache an MTA-STS policy for a week
  (`max_age`); an enabled policy lists the hostname of the new server once
  the domain moved, so publish it and keep the old host reachable for
  that time.
- **Both servers may serve the domain for a short time:** the old one
  until its new revision is rolled out, the new one from its own.
- **The old server's other domains.** If the old server's normal
  configuration cannot be applied at that moment (the directory or the
  users Secret is missing, or the new revision is still validating),
  the fail-closed render replaces it and takes its remaining domains down
  until the blocking input is fixed
  ([domain authorization](../concepts/domain-authorization.md#revocation)).
  Move a domain while the old server is healthy.
- **The last domain leaving** leaves a server with `Ready` reason
  `NoDomains` and a fail-closed data plane.

A graceful move (queue drain, mailbox copy, ordered DNS changes) is in the
[backlog](../backlog.md).

## Deleting a MailDomain

Deleting the `MailDomain` removes its DNS records at once, with no grace
period ([ADR 0012](../decisions/0012-dns-records-and-dmarc.md)), and the
`MailServer` it referenced stops serving it with its next validated
rollout, like a revoked domain. In
`externalDNS` mode the `DNSEndpoint` it owns is garbage-collected, so
external-dns removes every DKIM record, including those of retiring
keys: mail that is still queued and was signed then fails DKIM at the
receiver. The key Secrets stay.

Keep your GitOps tool from pruning the `MailDomain` by accident:

- Argo CD: `argocd.argoproj.io/sync-options: Prune=false`
- Flux: `kustomize.toolkit.fluxcd.io/prune: disabled`

In `manual` mode the records stay in your zone until you remove them.
