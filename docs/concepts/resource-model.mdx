# Resource model

CNMS v1alpha1 (API group `cnms.rpp.gmbh`) currently defines six resources.
Five of them are namespace-scoped: a tenant's mail system lives in one
namespace, and every reference between CNMS resources stays inside that
namespace (name-only references, no cross-namespace RBAC), with one
exception, the `serverRef` of a `MailServiceAccount`, which needs the consent
of the server. The sixth, `MailDomainGrant`, is cluster-scoped and
admin-owned.

The full API reference is [generated from the Go types](../reference/api.md)
(`make api-ref`). Design decisions are recorded in
[ADR 0002](../decisions/0002-v1alpha1-api-design.md) and
[ADR 0003](../decisions/0003-security-defaults-and-domain-ownership.md);
the domain-to-server binding is
[ADR 0014](../decisions/0014-domain-server-binding-and-hostname.md).
How domain authorization works is explained in
[domain authorization](domain-authorization.md).

## The resources

:::note
Not every resource has a controller yet. `MailServer`, `MailDomain` and
`MailDomainGrant` are reconciled, and so is `MailUser`: its controller
writes the status and the credential Secret, and the `MailServer` renders the
accounts (see [users and aliases](../how-to/users-and-aliases.md)).
`MailDomain` generates and rotates DKIM
keys and lists and verifies its DNS records
([how-to](../how-to/dkim-keys-and-dns-records.mdx)), and the `MailServer`
hands the active keys to Rspamd ([DKIM signing](dkim-signing.md)).
The `MailDirectory` controller validates its configuration and probes the
directory, but nothing renders a directory into Postfix or Dovecot yet: the
`MailServer` controller reads only its existence. The `MailServiceAccount`
controller checks the consent, the sender and the directory and makes the
credential Secret and the egress policy, but the `MailServer` does not serve
the accounts yet, so they have no effect on mail
([how-to](../how-to/service-accounts.md)). See the
[roadmap](../roadmap.md) for the phase of each part.
:::

### `MailDomainGrant`

Grants one namespace the right to use one domain for mail (sending,
receiving, DKIM signing, certificates, DNS records). Cluster-scoped and
admin-owned; the object name is the domain itself, so there is exactly one
grant per exact domain and the name is normalized by the API server.
`spec.namespace` names the tenant; `spec.includeSubdomains` (default
`false`) also covers subdomains, with more specific grants taking
precedence. The operator enforces the grants and fails closed; without a
matching grant a domain is inactive.

### `MailServer`

A tenant-facing mail system: inbound (port 25) and submission (port 587)
services, outbound delivery, and mailboxes. One `MailServer` is fully isolated
from any other: own workloads and queues, own sending addresses, own DKIM
keys, own Rspamd and Valkey instances. Nothing is shared between
`MailServer`s, so their sender reputation stays independent.

Key spec fields:

- `hostname` — the name the server presents (required, mutable): HELO,
  the name of the certificate, the target of the MX records of its domains
  and the `mx` host of their MTA-STS policies. It is authorized through a
  `MailDomainGrant` like a domain and unique among the competing servers
  ([domain authorization](domain-authorization.md#the-hostname-of-a-server)).
  Create its `A`/`AAAA` records at the inbound address:
  `status.records` lists them and whether a lookup verified them. A
  hostname that is not authorized does not take the domains down; the
  server presents the name of its Postfix Service instead
  (`HostnameAuthorized=False`).
- `spf` — the sending sources of the server (`ip4`, `ip6`). They are
  added to the SPF record of every domain the server serves and make up
  the SPF record of the hostname, which is the HELO identity.
- `directoryRef` — the `MailDirectory` used for recipient validation and
  authentication. Optional (ADR 0008): without it the server needs another
  user source, otherwise it is not ready (`NoUserSource`): `MailUser`s that name
  the server, or, for tests, `submission.insecureStaticUsers`. A server has one
  source.
- `outbound` — exactly one of `direct` (own sending addresses, optionally via
  a `MailIPPoolClaim`) or `relay` (a smart host; the `MailRelay` resource
  arrives with the relay phase).
- The domains it handles are not listed here: every `MailDomain` of the
  namespace that names the server in its `spec.serverRef` is accepted for
  delivery and submission once authorized, and its outbound mail is signed
  with the DKIM keys of the `MailDomain`. `status.domains` lists them, with
  `served` and the `reason`; a server without any `MailDomain` is not ready
  (`NoDomains`).
- `serviceAccounts.allowedNamespaces` — the namespaces whose
  `MailServiceAccount`s may reference the server: a list of objects with a
  `name` and optional `senderDomains` (domain names of the server's domains
  that the namespace may send from; unset means every served domain, and an
  empty list is refused). Unset or empty, no other namespace may; accounts of
  the namespace of the server need no entry. The `MailServiceAccount`
  controller evaluates it ([how-to](../how-to/service-accounts.md)).
- `tls` — the cert-manager issuer the server certificate comes from.
- `submission`, `mailboxes` — enable submission (on by default) and Dovecot
  mail storage (off by default). With submission on and mailboxes off,
  Dovecot runs in auth-only mode.
- `postfix`, `rspamd`, `valkey` — workload tuning (replicas, queue storage,
  Valkey persistence) with defaults that match the HA requirements.
- `availability`, `observability`, `backup` — PDB/topology spread,
  Prometheus Operator integration (`auto`/`enabled`/`disabled`), and k8up
  backup annotations.

### `MailDomain`

Owns the public DNS records of one domain: DKIM (selector + key rotation with
overlap), SPF, DMARC (DMARC1 / RFC 9989-9991 semantics for the records CNMS
publishes), MTA-STS, and TLS-RPT.

- `serverRef` — the `MailServer` of the same namespace that serves the
  domain (required). It may point at a server that does not exist yet
  (`ServerFound=False`; keys and records are still generated). It is
  mutable: changing it moves the domain to another server
  ([how to move a domain](../how-to/dkim-keys-and-dns-records.mdx#move-a-domain-to-another-server)).

- `dnsMode` is `manual` (default) or `externalDNS`. In manual mode the status
  lists every required record and whether a lookup verified it; the admin
  creates the records with the hoster. In `externalDNS` mode the operator
  creates `DNSEndpoint` resources.
- DKIM configuration is spec. Either the operator generates the keys
  (`selectorPrefix`, optional `ed25519` second signature, rotation `interval`
  and `overlap`, default overlap 120h so deferred mail stays verifiable), or you
  bring your own keys by Secret reference in `keys` (the recommended production
  setup; you own the selectors and the rotation schedule). Generated selector
  names are `<prefix>-<yyyymmdd>` (UTC creation date of the key), so a
  rotation publishes a new selector next to the old one. The rotation
  schedule progress is recorded in the `cnms.rpp.gmbh/rotation` annotation so
  it survives a restore without status.
- `spf` lists the sending sources of the domain (`ip4`, `ip6`, up to 5
  `include`s and a `qualifier`), on top of the ones of its server
  (`MailServer.spec.spf`); `dmarc` can set `subdomainPolicy` and
  `nonExistentSubdomainPolicy`; `mtaSts` is report-only and has a `mode`
  (CNMS does not serve the policy); TLS-RPT needs a report address in
  `tlsRpt.rua` or `dmarc.rua`.
- `status.records` is the contract for DNS verification: every required
  record with name, type, expected value, and `verified` state. Besides the
  TXT records it lists the `MX` record of the domain, which points at the
  hostname of the server (reported and verified, not published).

### `MailDirectory`

Points at the external user directory (accounts are managed outside CNMS):
`ldap` or `sql` (PostgreSQL), credentials via Secret references. It backs
Postfix recipient validation (unknown recipients tempfail when the directory
is down) and Dovecot authentication (submission and IMAP). `status` carries a
`Ready` condition (valid configuration) and a `Reachable` condition (the last
probe, a warning that never takes a rollout away).

The API names only attributes and relations, never queries. For `ldap`,
`attributes` gives the attribute of the login name (default `uid`), of the
primary address (default `mail`, single-valued) and, optionally, of further
addresses (`aliases`, multi-valued), and `activeFilter` is a static
restriction such as `(mailEnabled=TRUE)` that every lookup adds (it has no
placeholder). For `sql`, `users` and `aliases` name a relation each (table or
view, with an optional `schema`); the column names are fixed (`login`, `mail`,
`password`; `alias`, `target`), so an existing schema is adapted with views.
Design: [ADR 0015](../decisions/0015-user-sources-directory-users-and-aliases.md).

### `MailUser`

An operator-managed account for a server without a directory
([ADR 0015](../decisions/0015-user-sources-directory-users-and-aliases.md)).
The object name is the login and the local part of the primary address:
`alice` with a `domainRef` to the `MailDomain` of `example.org` (named
`maildomain-sample` in the sample) is `alice@example.org`. The name is a
DNS-1123 subdomain of at most 64 characters (dots allowed, as in
`alice.smith`); names starting with `sa.` are reserved for service
accounts. `serverRef` and `domainRef` are same-namespace references, and the
domain has to be served by that server. `aliases` (at most 32) are further
`localPart` and `domainRef` pairs, also in other domains of the same server:
they deliver into the same mailbox and the account may send as them, but they
are not login names. The local part is lower-case ASCII letters, digits and
`.` `_` `-`, up to 64 characters, starting and ending with a letter or digit,
without `..` and without `+`. A duplicate alias, and an alias equal to the
primary address, are refused at admission. `disabled` stops the login and the
right to send, and mail keeps arriving. The password is generated by the
operator, or comes from the key `password` of `passwordSecretRef`.

`status` has room for the canonical `address`, one entry per address in
`addresses` (`kind` primary or alias, `served`, `reason`), the
`credentialSecretName`, a non-secret `credentialRevision`, and the
conditions. The `MailUser` controller writes this status and the credential
Secret, and the `MailServer` renders the accounts. A `MailServer` has either a
`directoryRef` or `MailUser`s.

### `MailServiceAccount`

The sending credential of an application
([ADR 0008](../decisions/0008-user-sources-and-service-accounts.md),
[ADR 0015](../decisions/0015-user-sources-directory-users-and-aliases.md),
section 4.9). It lives in the namespace of the application; its name is at
most 63 characters. `serverRef` names
the `MailServer` and may carry a `namespace`; without one it is a server of
the namespace of the account. A server of another namespace takes effect only
when that server lists the namespace in `serviceAccounts.allowedNamespaces`.
`sender` is the one address the application may send as: a lower-case
address whose local part has the rules of an alias (up to 64 characters of
ASCII letters, digits and `.` `_` `-`, starting and ending with a letter or
digit, no `..`, no `+`) and whose domain follows the rule of
`MailDomain.spec.domain`. That the domain is served by the server and
authorized for the namespace cannot be checked by the API server; the
controller does.

`status` has the `observedGeneration`, the conditions, the name and the
revision of the credential Secret, and the `admittedSender`. The controller
makes a Secret `<name>-credential` with the connection values for the
application and a NetworkPolicy `<name>-submission` in the namespace of the
account, and removes both when the namespace or the sender is revoked. The
`MailServer` does not serve the account yet.

## How they fit together

```
MailDomainGrant ──authorizes──> namespace + domain   (admin-owned, cluster-scoped)
MailServer ──references──> MailDirectory   (auth + recipient validation)
MailDomain ──serverRef──> MailServer       (DKIM signing, submission domains)
MailUser ──serverRef──> MailServer         (account of a server without directory)
MailUser ──domainRef──> MailDomain         (primary address and aliases)
MailServiceAccount ──serverRef──> MailServer   (application credential; another
                                                namespace needs allowedNamespaces)
MailDomain ─── publishes ──> DNS records   (DKIM/SPF/DMARC/MTA-STS/TLS-RPT)
MailDomain ─── MX ───> MailServer hostname (reported and verified; the hostname
                                            carries A/AAAA and SPF records)
```

A `MailDomain` references the one `MailServer` that serves it; a server
serves every domain that references it. A `MailDomain` is only active for
its domain when a `MailDomainGrant` names its namespace (or the operator
runs unrestricted); without one, the domain is inactive and fail closed.
The hostname of the server is granted the same way and is judged on its own,
so a missing grant for it does not stop the server from serving its domains.
The `MailServer` controller evaluates the grants for the hostname and the
domains attached to it at reconcile time; the API server enforces only the per-object
rules (schema, defaults, CEL).

## What is not here yet

Resources for the later phases are added in the phase that implements them,
so their fields are designed with implementation feedback:

- `MailRelay` (phase 6), `MailIPPoolClass` / `MailIPPool` /
  `MailIPPoolClaim` (phase 7), `InboundRoute` (phase 8), `MailPolicy` (phase
  9).

State that cannot be recomputed from the world (bindings, rotation schedule
progress) lives in spec or annotations, never only in status: custom resources
are restored from GitOps, which contains no status at all.
