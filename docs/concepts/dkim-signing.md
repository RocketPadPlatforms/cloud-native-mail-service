# DKIM signing and rotation

:::note
API version `v1alpha1`. Design: [ADR 0011](../decisions/0011-dkim-keys-and-rotation.md)
(keys, mounting, rotation) and [ADR 0013](../decisions/0013-never-unsigned-guard.md)
(the guard). Steps: [DKIM keys and DNS records](../how-to/dkim-keys-and-dns-records.mdx).
:::

## The rule

Mail of a served domain that comes from an authenticated sender, or from
Postfix itself (`sendmail`, re-injected mail), **leaves signed or does
not leave**. Everything else is never signed by CNMS: unauthenticated mail
from the Internet or from other pods, and bounces that Postfix generates.

The rule is one invariant, independent of how the keys are provided or
rotated, and it is enforced where the signature is made, in Rspamd.

## Who does what

- The **`MailDomain` controller** owns the keys: it generates RSA-2048
  (and optionally Ed25519) keys into immutable Secrets, or reads the
  Secrets you reference, and rotates them. It records which keys are
  active in the `cnms.rpp.gmbh/rotation` annotation, because that
  progress has to survive a restore without status.
- The **`MailServer` controller** gives the active keys of the domains it
  serves to its Rspamd pods: a projected, read-only volume holds one file
  per key, and the rendered configuration names the files and selectors.
  Key bytes are never in a ConfigMap, a hash or a pod template.
- **Rspamd** signs with every active key of the header-From domain
  (dual signing: one RSA and one Ed25519 signature) and a small guard
  checks the result.

## The guard

Rspamd does not stop a message it could not sign: with a missing key it
logs an error and passes the mail on. The guard turns "should have been
signed" into a deferral. For every message of a signed class from a
served domain it checks that the signature of each active key is there;
if not, the message is answered with a temporary failure, Postfix replies
`451 4.7.1` at the end of DATA, and the sender keeps the mail and retries.

A domain that is served but has no usable key (no key yet, a Secret that
was deleted, a key that does not parse) therefore sends nothing until it
has one. Its inbound mail is not affected, other domains are not
affected, and the rollout of the `MailServer` does not wait: the
`DKIMKeysAvailable` condition names the missing key. A signing key never
depends on Valkey, so a Valkey outage does not change any of this.

The guard is tested against the pinned Rspamd image on every pull
request: which mail is signed, which is deferred and which is left alone
(see [the guard matrix](../reference/testing.md#the-guard-matrix)).

## Rotation

With `spec.dkim.rotation` the operator creates the next key when the
active one is older than the interval and publishes its record as
**pending**: it is in DNS but does not sign. It becomes **active** only
after its record has been verified for a hold period, and the previous
key becomes **retiring**: still in DNS (so mail signed with it and still
queued can be verified), no longer signing. When the overlap ends, the
record and the key Secret go away. The overlap has to cover the Postfix
queue lifetime (5 days by default).

The data plane follows the active keys only. When the active key
changes, the signing configuration and the guard table change with it,
so the switch goes through the validation Job and a rolling update of
Rspamd like any other configuration change; the old pods keep signing
with the old key until the new ones are ready. With your own keys,
rotation is a change of the `signing` flags in your repository, with the
same data plane behaviour.

## Limits

- The guard does not check that the login matches the sender address:
  any authenticated user can send as any served domain until the envelope
  sender binding and the header From ownership check exist (backlog).
- A message with several `From` addresses, one of them in a served
  domain, is rejected with `554 5.7.1`, because it can never be signed.
- Authenticated mail whose `From` header is missing, has no domain, or
  is not in a domain the server serves (a subdomain of a served domain
  counts as unserved) is rejected with `554 5.7.1`; it could only leave
  unsigned. This also refuses a mail client's "redirect" or "resend" that
  keeps the original foreign `From`, and applications that send with a
  `From` outside the served domains.
- Bounces and notifications generated by Postfix are not signed
  (ADR 0013).
- Not verified on a cluster yet: how fast a changed key Secret reaches
  the pod, and what the kubelet does to the permissions of the projected
  volume (checked only in the pinned Rspamd image with equivalent file
  owners and modes). The e2e suite covers both.
